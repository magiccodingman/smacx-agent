# MCP tool reference

- `smac_status()` — process identity and menu/game state.
- `smac_new_game(...)` — launch a configured random single-player match semantically.
- `smac_launch()` — launch only the visible isolated game window.
- `smac_snapshot()` — compact fair-play turn state, current ready-unit references, protocol phase, current guard, latest deferred-action status, and latest publicly displayed Council result.
- `smac_decision(..., detail="compact")` — preferred action-ordered loop: a revision-stable player-state headline plus the exact active interaction, selected ready unit choices, wait/gap directive, or game-management choices. It retries assembly if state changes between observation and enumeration. Compact is the default and avoids replaying the comprehensive snapshot on every unit; use `detail="full"` only for one decision that genuinely needs the complete turn document. Set `finish_ready_units=true` only after deliberately deciding every remaining unit is finished; this returns the exact guarded skip-all/game-management frame and conflicts with selecting one `unit_id`.
- `smac_list(kind, ...)` — bases, units, factions, technologies, or known/visible tiles.
- `smac_choices(kind, ...)` — enumerate interaction, research, allocation, Social Engineering, diplomacy, Council, Unit Workshop, production, base-management, base-citizen, unit, or game-management choices.
- `smac_command(...)` — execute exactly one returned choice with `match_id`, `session_id`, and `expected_revision`.
- `smac_wait(seconds)` — bounded wait while the engine or another faction owns the turn.
- `smac_chat(...)` — list or send guarded native LAN chat scoped to the current match/session and optional recipient faction. It persists delivered speech with network-player/faction associations and exactly-once attention state.
- `smac_lan(...)` — inspect, host, discover, join, configure, ready, and start the validated native DirectPlay LAN lifecycle.
- `smac_saves(action, match_id, slot)` — list or load match-scoped save slots. Stop the current game before load.
- `smac_knowledge(action, match_id, ...)` — list/get/history or record durable match facts in the authoritative scoped SQLite store. Writes require the active `session_id` and current snapshot `revision`; corrections retain audit history and the former JSON ledger is only a compatibility mirror. Session-local unit/base/prototype engine IDs are rejected.
- `smac_memory(...)` — retrieve the bounded working set, scoped FTS5/BM25 search, batched recall, chat/events, structured projection histories, or optional Graphiti projection status. It cannot widen `(match_id, agent_id, perspective_id)` or execute arbitrary SQL.
- `smac_memory_update(...)` — create or revise one guarded claim, belief, relationship, commitment, goal, or summary from a JSON record. Actor/evidence references are mechanically constrained to the same perspective, and claims remain distinct from beliefs.
- `smac_report_capability_gap(...)` — record one missing semantic capability, deduplicate repeated reports for that session, and latch commands plus launch/new/load. Only a developer MCP restart followed by a fresh session after bridge development can resume play.
- `smac_stop()` — terminate only this project's isolated game processes; MCP stays running.

Current command families are exposed in the live MCP schema. Prefer `smac_decision`; use `smac_choices` for strategic/specialized queries. Never guess command strings or engine IDs: copy one returned action and guard, execute it, then obtain a new frame.

`smac_lan` can launch the isolated visible game from an inactive menu, host a named DirectPlay session, discover sessions at a supplied IPv4 address, and join exactly one freshly returned opaque `network_session_id`. In the stock lobby, follow `legal_actions`: the host may apply the validated `small_easy` profile, a client may ready, and the host may start only when all clients are ready. Every lobby mutation copies the current match/session/lobby revision and uses a unique idempotent `client_operation_id`. Arbitrary lobby settings are not inferred from menu coordinates.

Human LAN diplomacy uses the native paired `DiploWindow`, not chat or UI input. A fresh diplomacy family marks a contacted human target with `human_controlled=true`; `open_diplomacy` queues the stock `0x1502` handshake. Because that 1999 protocol has no receiver-ready acknowledgment, re-observe the queued action: if a collision returns both clients to their ordinary phases, enumerate a fresh channel and retry rather than replaying an old request. The `human_diplomacy` interaction returns exact participants, acceptance state, and structured clauses. `propose_human_relationship` returns only relationships legal from current public state: Treaty without another peaceful relationship, Pact from Treaty, or Truce from Vendetta. `propose_human_technology` enumerates only caller-owned named technologies the counterpart does not own. One compact `propose_human_energy` descriptor supplies `amount_min=1` and a fresh `amount_max` equal to the caller's treasury; pass the chosen integer as `amount`. Each outgoing proposal command atomically adds, network-drains, verifies, and commits its exact clause so the proposer cannot strand itself between separate compose/accept calls. The peer must inspect the synchronized clauses and use its fresh `respond_human_diplomacy` accept or decline choice. `finish_human_diplomacy` only ends a still-open transmission. A received technology becomes a queued `technology_presentation` advanced with its returned semantic command; LAN does not enter SMACX's bridge-starving private presentation loop. Once a paired window closes, snapshots temporarily return `waiting_for_engine`; this mechanically blocks ordinary mutations while final DirectPlay packets settle. On `stale_state`, re-enumerate and execute only if the same intended choice is still returned. Re-observe ownership, treasuries, relationships, and phase before continuing. Human map and joint-attack offers remain absent until their packet paths are separately validated.

Map locations cross the MCP boundary only as opaque match-local `tile_id` values. They are stable within a running map, but their numeric values are identifiers—not coordinates: do not calculate distance, direction, or adjacency from them. Obtain IDs from `ready_unit_refs`, base/unit records, `smac_list(kind="tiles")`, or an exact action choice. Use `center_tile_id` when listing a neighborhood and `target_tile_id` when querying or executing a map-targeted unit action. Native x/y coordinates are neither returned nor accepted; the DLL alone resolves a valid tile ID and rechecks visibility, knowledge, range, terrain, diplomacy, and unit rules.

`smac_snapshot` includes `ready_unit_refs` whenever owned units still require a decision. Each entry is deliberately compact—current unit ID, name, opaque tile ID, and role flags—and shares the snapshot revision. It eliminates a separate full-unit listing for the ordinary action loop while preventing guessed IDs after production, founding, combat, or capture reorders the native unit array.

`game_management` always describes match-scoped save support. It returns executable `end_turn` only when no owned unit needs a decision; otherwise it returns the non-executable `turn:end_blocked` status, exact `ready_unit_count`, and one `skip_all_ready_units` tuple listing the complete current ready-unit IDs. That tuple is a deliberately narrow context-saving action: it requires `confirm_skip_all_ready=1` plus the returned count, spends each listed unit with native skip, and never batches movement, combat, production, or another interruptible action. The identity/revision guard fixes the set before mutation; an omitted confirmation, changed count, or replay is rejected. Native preferences may immediately advance the turn after the last skip, so observe instead of assuming a later `end_turn` call is required. Execution independently rejects an invented early end-turn request. If SMACX still raises `REALLYOVER` for a native-automated unmoved unit, fresh interaction choices expose cancel/proceed through `respond_to_end_turn_confirmation`. After proceed, `turn:transition_pending` replaces `end_turn` until the native turn actually changes, preventing a duplicate submission during the re-entrant modal handoff.

Reviewed base notices expose structured information alongside `acknowledge_popup`. Starvation, convoy cancellation, population limits, nutrient shortage, drone-riot transitions/destruction, Golden Age transitions, power-shortage destruction, and governor psych requests identify their event and the affected owned base when the native context provides it. Facility/unit/prototype completion notices report the displayed base and item, whether a governor chose follow-up production, and queued-item count when applicable. Re-list the base after acknowledgement.

An Alien Artifact entering an owned base exposes the exact native `ARTIFACT` alternatives through `respond_to_artifact`. `no_action` retains the unit. `link_technology` discovers one native-available random technology; `accelerate_production` appears only for the exact current Secret Project or unprototyped unit and reports its mineral context. Both permanently consuming paths require `confirm_consume_artifact=1`. The originating move remains the authoritative deferred action and completes as `native_artifact_consumed` after any resulting technology notice is resolved.

`base_management` provides base rename, primary/prioritized governor configuration, every native named advanced governor permission, and future production-queue edits. Advanced permissions are returned as one opposite-state `set_governor_permission` toggle each: multiple priorities; exploration, land/naval/air combat, native life, land/air defense, prototype, transport, probe, Former, and Colony Pod units; facilities; forced psych; Secret Projects; and production hurrying. Each change also updates the faction default inherited by future new bases. When an active governor manages production, the choice warns that the native governor will clear future queue entries and immediately recalculate. `base_citizens` returns the visible 21-tile base radius with actual yields plus legal specialist types; manual assignments are blocked until governor citizen management is disabled. Destructive unit disbanding requires both a fresh unit choice and `confirm_disband=1`.

Diplomatic demands return explicit terms where the engine exposes them. Technology demands return the exact one-to-four-item native bundle, `demanded_count`, and `context_complete`; concession is withheld if any named item is invalid, duplicated, or no longer owned. The eligible single-technology variants may return `response="counter"` with `payment="energy"` and the exact native quote or `payment="technologies"` and one exact counterpart-owned reciprocal technology. If the counterpart rejects that price, the real follow-up exposes fresh accept/reject choices for the original demand. Energy tribute includes the full amount, native lower counteroffer, and affordability; joint-war requests identify the requester and target. `response="accept"`, `"reject"`, or (only when returned) `"counter"` maps to the reviewed native result path without mouse, keyboard, or coordinate input.

Territorial and hostility popups expose `respond_to_territorial_incident` only while the exact native label is active. Withdrawal demands return the counterpart plus withdraw, mutual-withdrawal, or refusal choices. Encroachment and treaty/truce/Vendetta warnings return cancel or proceed/declare choices. Any branch that can start hostilities requires the returned `confirm_hostility=1`; omission is rejected without dismissing the dialog. These popups may belong to a pending `move_unit`, so resolve them before any other turn action and wait for that original action ledger entry to finish.

Native `BADIDEA`, `GOODIDEA`, and `GOODIDEA2` combat-odds confirmations, plus the reduced-strength `HASTY` assault prompt, expose `respond_to_combat_confirmation`. The structured context identifies the queued action, attacker, target, visible defender, qualitative warning, and exact displayed odds or HASTY current/full strength when the native dialog supplies them. Cancel is always safe; proceed requires the exact fresh `confirm_attack=1` tuple. A hasty proceed may next open a treaty/truce warning and then a normal odds confirmation; resolve each fresh interaction in order while retaining the original action ID. Both paths ultimately resume that deferred movement/combat ledger entry.

Endgame decisions and passive native presentation windows remain semantic. `ACCEDE`/`ACCEDECOOP` expose the elected faction and return `respond_to_supreme_leader`: accession follows the native victory path, while defiance requires the exact fresh `confirm_defiance=1` tuple. `victory_interlude`, `credits`, `score_report`, `quayle_rating`, `hall_of_fame`, and `replay` each return one `advance_endgame_presentation` choice carrying the exact phase; this invokes the visible native window's own close callback without UI input. After final scoring, `GAMEOVERMAN` returns `respond_to_game_over` choices to finish or continue the completed match. Strategic and unit mutations are phase-gated throughout. Optional external victory movies are disabled by the default `narrative_ui=false`; they are not a semantic window when narrative UI is explicitly enabled.

When economic victory is enabled, its prerequisite technology is owned, and the faction has a Headquarters, `game_management` exposes the same aggregate Global Energy Market cost available through the native HQ menu. An affordable plan returns `corner_global_energy_market` with `confirm_corner_market=1`, exact cost, Headquarters, and countdown length. After commitment, the exact treasury deduction and completion turn/year are returned; later `game_management` families report the active plan. Capturing the Headquarters can still foil the plan under native rules.

Native `ENERGYLOAN*` and `ASKFORLOAN*` interactions expose the principal, payment per turn, term, scheduled total, direction, counterpart, and current affordability. Accept, reject, or the returned half-principal counteroffer only through `respond_to_diplomatic_offer`. `smac_list(kind="factions")` reports both sides' known outstanding balance and payment for each contacted faction, so the model can track obligations without remembering hidden engine state.

When the native `COUNTER1` gift menu contains its energy-payment row, that row is exposed as `give_energy_gift` rather than as a free-form text dialog. Copy an amount within the fresh `amount_min`/`amount_max` bounds. The bridge closes the suspended selector safely, invokes the game's native `make_gift` path, drives its nested amount and receipt windows on the UI thread, restores the unoffered treasury balance, and verifies both factions' exact deltas before returning success.

Technology purchases expose the exact unowned technology ID/name/category, price, counterpart, and affordability; acceptance is revalidated against current credits and ownership. Technology-sale offers expose the owned primary technology and, only when the native `ENERGYTECH2` dialog supplies one, an alternate technology counteroffer at the quoted price. The Datalinks button is unnecessary because all decision-relevant terms are already structured. Native rejection and insufficient-credit notices are reviewed information-only interactions rather than visual dead ends.

Prototype and commlink purchases use the same guarded offer contract. A prototype offer distinguishes its canonical Unit Workshop design name from the decorated native dialog text, and acceptance is revalidated against the exact source design and price. A commlink offer identifies both the seller and target faction; acceptance revalidates that the target frequency remains unowned. The `PROPOSECOMMLINK`, `PROPOSEATTACK`, and `PROPOSEBASE` native selectors expose only IDs actually present in their native lists plus a semantic cancel action. Proposal IDs are engine IDs, not visual row positions.

Ordinary `METFRIEND*`/`METALIEN*` introductions expose the exact third-party commlink target and free, technology, or energy terms. `ENEMYMAP*`, `BOTHFRIEND`, and `BOTHFRIENDALIEN` expose the named map target and exact energy or owned-technology price without revealing the purchased map before acceptance. `ANYNEWS` and `ANYALIENNEWS` share the reviewed commlink-sale contract.

Reciprocal commlink bargains are also typed. `ANYNEWS` names the already-known frequency another leader wants and the energy payment the player will receive. `COMMLINKTECH` names the unowned target frequency and exact player-owned technology requested in exchange. Acceptance is suppressed or rejected if either asset has changed since the fresh choice.

In LAN, AI contact is deliberately narrower than single-player bargaining. A local `COMM`/`COMMDIPLO` may be accepted, its `INTRO*` greeting continued, reviewed passive relationship notices acknowledged, and the `DIPLO` conversation finished. A fully described technology trade/demand or Treaty/Truce/Pact offer may be rejected. Consequential acceptance and concessions stay absent from the multiplayer allowlist until the exact native transfer is proven on both clients.

Native `PAYBASESWAP` and `TECHBASESWAP` negotiations identify the exact counterpart-owned base. The energy branch includes price and live affordability; the research branch explicitly states that every currently owned technology will be shared. Acceptance revalidates ownership and funds before allowing the native cession/payment or all-technology exchange to finish. Re-list bases after any accepted transfer because capture can reorder engine IDs.

Native `MAYBEWARPRICE` and `MAYBEWARTECH*` joint-attack counteroffers identify the counterpart and proposed enemy plus either the exact energy price or the complete requested bundle of one to four technologies. Acceptance revalidates target life, affordability, and every owned technology before the executable performs payment and begins Vendetta; rejection pays nothing.

`council` returns `convene_council` only when the native engine says a Council may be called. The resulting `COUNCILISSUES` interaction exposes exactly the proposal IDs present in the native list. `choose_council_proposal` takes the candidate or YEA/NAY ballot bundled with that proposal; the visible Council chamber resolves through its native vote routine and `snapshot.last_council_result` records the public outcome. When another faction calls the Council, acknowledge `CALLSCOUNCIL` once; replay is rejected after that exact popup closes. The bridge then recognizes the separate native Council window and exposes its candidate or YEA/NAY ballot through fresh `interaction` choices rather than reusing the old guard or closed popup object.

Pre-vote `BUYVOTEYEA*`, `BUYVOTENAY*`, `BUYVOTEABSTAIN*`, and `BUYVOTEGOV*` bargains expose the exact requested ballot, counterpart, energy price, affordability, and complete technology alternative when one exists. `respond_to_council_vote_bargain` accepts only `none`, `energy`, or the entire returned technology bundle; ownership and funds are revalidated before the native commitment resolves.

Incoming Governor-vote purchases use `respond_to_incoming_vote_offer`. `VOTEFORME` exposes the exact energy payment; `VOTEFORMETECH` exposes the two native technology IDs and names. Accepting is consequential and requires the returned candidate plus `confirm_vote_commitment=1`; rejecting requires no confirmation.

`unit_design` returns unlocked chassis, weapon, armor, reactor, and ability catalogs plus currently available prototypes. When `ASKSEEDESIGN` appears, `respond_to_design_offer(response="open")` dismisses the coordinate-oriented native offer and returns `next_choice_kind="unit_design"`; take a fresh snapshot, then request that choice family. `create_unit_design` accepts at most two compatible ability IDs and lets the native prototype engine make the final acceptance decision. `retire_unit_design` is limited to owned custom designs with no unit or queue references and requires `confirm_retire=1`. `upgrade_prototype` quotes the full energy cost before requiring `confirm_upgrade=1`; it upgrades all owned units and queue references only along a conservative, non-downgrading same-chassis combat path. These mutations are currently single-player only.

`unit_actions` gives boarded passengers priority over ordinary movement. A passenger may `remain_boarded` or use an atomic `disembark_unit` choice onto adjacent known land; a co-located transport with free capacity exposes `board_transport`. Drop Pod units at a base/airbase receive up to 128 nearest visible native-validated `airdrop_unit` targets. Artillery exposes only currently visible non-pact stacks in native range, and `artillery_attack` requires a fresh observation afterward because combat can change vehicle IDs.

A ready vehicle receives one `upgrade_unit` choice per exact native-legal owned custom design. Each choice quotes the one-vehicle energy cost, affordability, prototype status, and `confirm_upgrade=1`. Execution changes only that vehicle, applies the native Trained-morale adjustment, prototypes the target when needed, charges the quoted cost, and consumes the vehicle's remaining turn. Fabricated or downgraded targets are rejected, and the all-units `upgrade_prototype` action remains a separate Unit Workshop command. LAN execution is withheld until its native synchronization path is validated.

An unboarded unit standing on a currently visible tile owned by a living Pact faction may expose `give_unit`. Air units require a base or airbase, and transports carrying cargo are withheld so one confirmation cannot silently transfer additional units. Copy the returned faction and `confirm_transfer=1`; the bridge calls the native ownership-change routine, verifies the new owner, and then the unit normally disappears from `scope="own"`. It may also disappear from `scope="visible"` immediately, which is fair-play behavior rather than transfer failure.

Missiles use compact two-stage targeting. First request `unit_actions` without a target to read the missile kind, maximum range, and fair-play target requirements. Select a `tile_id` only from visible/known semantic state, then request fresh `unit_actions` for the same unit with that `target_tile_id`. Execute `launch_missile` only if that exact query returns it. Conventional missiles require a visible hostile at war; tectonic and fungal payloads require a visible empty tile and respect territorial diplomacy; Planet Busters require a visible hostile asset in the blast area, reject visible owned or Pact assets in it, and require an explicit `confirm_atrocity=1`. A launch consumes the missile and can shift unit IDs, so re-list units immediately.

Ready units may set `patrol_unit` to one known, native-validated waypoint. Ready land formers with the required technology may set `build_road_to` in road or Mag Tube mode toward a different known land tile. These are persistent native orders: while one is active, `unit_actions` exposes only `activate_unit` rather than allowing an accidental second order, and the unit does not count against the end-turn decision gate. The engine resolves movement, construction, obstruction, and cancellation turn by turn.

A ready combat unit may select `auto_explore_unit`. This invokes the game's native Explore automation rather than bridge pathfinding, so discovery, movement costs, encounters, and future destinations remain engine-controlled. The unit reports `order_name="auto_explore"`, is removed from the ready-decision gate, and exposes only `activate_unit` until native waking cancels the automation. This is a fair-play player order: it grants no map knowledge to the agent and uses no pixels or coordinate input.

An off-base ready land or sea unit may receive one `return_to_base` tuple naming the native-selected nearest compatible known owned or Pact base. The command takes the returned `base_id`, never map coordinates, invokes the original `Console::go_home`, and verifies that its native waypoint exactly matches the fair-play candidate. Any unknown or changed destination is rolled back and rejected. The resulting `go_to` is persistent and activate-only. The broader object-ID route is two-stage: request `unit_actions` without `base_id` to receive `base_target:query`, choose one owned base from `smac_list(kind="bases")`, then request that same unit with the candidate `base_id`. A returned `go_to_base` resolves the coordinates internally and revalidates ownership, knowledge, land region or sea access, and aircraft remaining safe fuel range. The choice and command contain no destination coordinates.

Aircraft may also query a visible friendly standalone airbase through its `tile_id`. A returned `go_to` marks `destination_refuels=true` and `route_kind="air_recovery"`; it is exposed only within the aircraft's remaining safe fuel range. A non-refueling air destination is classified as `air_round_trip` and is limited to half the remaining range while departing a friendly refueling tile. Once an aircraft is away from such a tile, persistent non-refueling routes are withheld until it recovers. These checks are repeated during execution, so generic `go_to` cannot bypass a rejected `go_to_base`.

Carrier recovery uses an owned carrier `target_unit_id`, never its tile as a guessed destination. `recover_to_carrier` revalidates remaining fuel, reserves effective deck capacity, places the carrier under a derived recovery hold, and creates the native route to its current tile. The carrier exposes only `carrier_recovery_lock` while an aircraft is inbound or co-located but unboarded, so it cannot invalidate that route. On arrival, a fresh exact query exposes `board_carrier`; boarding creates native carrier-passenger state and refuels the aircraft. Loaded and inbound counts are observable, a full deck rejects another reservation, and boarded aircraft move with the native carrier stack. `activate_unit` launches a boarded aircraft at the carrier's current tile; `remain_boarded` keeps it aboard. These semantics are single-player-only until their LAN synchronization path is validated.

A ready combat unit can select `set_unit_on_alert`; a ready non-missile Air Superiority aircraft can additionally select `automate_air_defense`; and a ready Former can select `automate_former` with one currently eligible named policy: `full`, `roads`, `magtubes`, `improve_home_base`, `farm_solar_road`, `farm_mine_road`, `remove_fungus`, or `sensors`. Technology- or support-dependent modes appear only when their prerequisites are currently valid. These call the native `Console::automate`, remain outside the ready-unit gate, and expose only `activate_unit` while the unit remains under that policy. Observations distinguish them through `order_name` and `order_auto_type` (`auto_air_defense`/12 for Air Defense). Native Air Defense is real strategic delegation: SMACX may dispatch, lose, or remove the aircraft during turn processing, in which case re-list units instead of assuming it remains cancellable. Native patrol shares an internal state bit with automation, so the bridge additionally checks prototype role and exact automation mode; patrol continues to report ordinary `go_to` and `old_automation="none"`.

A ready owned non-missile combat aircraft may receive one `set_bombing_run` tuple per currently visible foreign base whose owner is at Vendetta. The target is an opaque `target_tile_id`; execution repeats visibility, ownership, diplomacy, readiness, and conservative non-sacrificial round-trip fuel checks before calling the stock bombing-run handler. The persistent native policy reports `order_name="bombing_run"` and `order_auto_type=10`, stays outside the ready-unit gate, moves under normal turn processing, and exposes only `activate_unit` to cancel it. The patched single-player host clears the stock handler's destination words during its synchronization round-trip, so the bridge restores only that exact already-validated destination after native acceptance. The action remains withheld in LAN until its packet path is validated.

A ready combat unit also exposes exactly one `set_designated_defender` choice whose `active` value is 0 or 1 and opposite its current Boolean `designated_defender` state. The native role toggle changes which unit the game prefers to defend a stack, does not consume movement, and is safe to combine with a later action after taking a fresh snapshot. Repeating the already-current state is rejected. LAN execution is withheld pending a dedicated synchronization regression.

An attack by a Nerve Gas Pod unit may open the native `USENERVE` interaction. `semantic_choices(kind="interaction")` identifies the pending attacker, visible defender, target tile, original action ledger, and whether the U.N. Charter is active. `respond_to_nerve_gas(response="conventional")` continues with ordinary weapons. Choosing `response="commit"` additionally requires the exact returned `confirm_atrocity=1`; a fabricated or unconfirmed atrocity is rejected while the native choice remains open.

A ready non-objective unit outside every base may expose `self_destruct_unit` in single-player. Its paired information record reports the reactor/weapon-derived blast damage and all owned or currently visible units on non-base tiles within the native one-tile radius, including projected lethal outcomes. It never reveals hidden units. Execution requires `confirm_self_destruct=1`, destroys the source, applies the original `action_destruct` stack damage, and can shift many unit IDs. The option is withheld in LAN until message `0x2407` synchronization is validated.

A ready combat unit or former on a compatible, visible, non-base tile receives one `destroy_terrain_improvement` choice per exact native-selectable improvement. Compound layers follow the original menu: a Soil Enricher must be removed before its Farm, and a Mag Tube before its Road. Execution requires `confirm_destruction=1`, is deferred through the authoritative `action_destroy` routine, consumes the unit's action, and publishes `native_terrain_improvement_destroyed`. A peaceful foreign owner also requires the returned `confirm_hostility=1` and receives the native reputation/Vendetta consequences. Pact territory exposes a non-executable rule status and fabricated commands are rejected. LAN execution remains withheld until its native packets are validated.

A ready Colony Pod receives executable `found_base` only on a native-valid site. Otherwise `unit_actions` returns non-executable `settlement:unavailable` rule status. It distinguishes an existing base tile, insufficient range from a fair-play-known base, incompatible land/ocean terrain, a Thermal Borehole, or an otherwise native-illegal site and includes the configured minimum plus nearest known range when safe to reveal. Hidden bases are never used to populate that explanatory range. Founding consumes the pod, so re-list units immediately.

Owned bases whose current Police rating permits it may expose `nerve_staple` in `base_management`. This is a destructive atrocity and requires the exact returned `base_id` plus `confirm_atrocity=1`. The command is deferred through the native game routine: success or immunity failure, ten-turn suppression, atrocity consequences, and information notices remain native. While stapling is active, the choice is suppressed and base observations report its remaining duration and attempt count.

A non-objective owned base containing an owned unit may expose `obliterate_base` in single-player. The first command only opens the game's native `OBLIT`/`OBLITOK` confirmation and returns an `action_id`; it does not destroy anything. Request fresh `interaction` choices. Cancel is consequence-free. Proceed requires `confirm_obliteration=1` and, only when current rules classify the act as an atrocity, `confirm_atrocity=1`. The bridge then lets the native command delete the base, apply diplomatic sanctions/notices, and publish `native_base_obliterated`. Base IDs can shift, so re-list bases afterward. Objective bases never expose the choice and fabricated requests are independently rejected.

Each physically built facility that the original recycle rules allow appears as a separate `recycle_facility` choice with its exact `energy_refund`. Execution requires `confirm_recycle=1`. Headquarters, an ocean base's Pressure Dome, faction-granted free facilities, and every facility after one has already been recycled at that base this turn are excluded. An artifact-linked Network Node is represented as permanent destruction with a zero refund. The command removes the facility, credits the original `5 * row cost` refund, sets the native per-base turn flag, and recomputes the base.

Probe teams adjacent to a currently visible non-pact base receive exact `execute_probe_mission` tuples. Supported native missions are infiltration, research theft, random or targeted sabotage, energy theft, drone riots, researcher assassination, standard or Total Thought Control when affordable, genetic plague when unlocked, and captive-leader rescue at an eligible Headquarters. Genetic plague is independently gated by returned `confirm_atrocity=1`. A targeted request remains pending while the native `VIRUS` menu is open: only then does `interaction` expose the production/facility/silo IDs actually present in that native menu. Use one returned `choose_probe_sabotage_target`; protected Headquarters and defense targets may then require a returned `respond_to_probe_sabotage_warning` decision. If the native targeted rate is zero, the game resolves random havoc without revealing a target list. Captive identities likewise remain absent from initial choices; only a successful native penetration opens `FREEWHO` and exposes its actual `choose_captive_leader` IDs. Frame variants use only already-contacted third factions and apply the selection only if the native success roll creates a framing opportunity. An adjacent visible isolated non-native unit may expose standard or Total `execute_probe_subversion`; its energy price is quoted with the same native vulnerability, faction, project, Probe-rating, Poly Encryption, and unit-role formula used by the game. Every operation requires `confirm_probe_incident=1` and fresh target/revision validation. Probe survival, success, retaliation, and incidental dialogs remain game-controlled.

A ready unit standing at an owned, unused Psi Gate receives `use_psi_gate` choices for every compatible owned destination gate. The command revalidates both bases, facility state, ownership, unit triad, and revision, invokes the native network-aware transfer, and consumes both endpoint gates for the turn.

No MCP tool exposes screenshots, mouse input, keyboard input, arbitrary UI text, raw memory, or scenario-editor state.
